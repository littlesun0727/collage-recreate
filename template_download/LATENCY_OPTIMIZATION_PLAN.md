# 拼贴素材下载流水线时延优化计划

日期：2026-10-25

状态：仅供讨论，尚未实施。本文件不改变正在运行的 1,000 张任务；等本批结束，再结合最终统计决定实施阶段和参数。

## 1. 目标与边界

目标是提高“每分钟新增有效候选”和“每小时自动保留模板”，而不是只增加请求数量。所有改动限于 `template_download`。

保留目前的数据标准：原文件保留、普通视频笔记排除、Live 封面与 MP4 配对、哈希与近似重复记录、每累计 100 张候选进入审核、分类每调用 20 张、定位每调用最多 5 张原尺寸图片、gpt-6-luna / low / Standard，以及边界检测后仅允许收缩的比例微调。

本批目标是 1,000 张初筛候选，不是 1,000 张最终通过模板。后续性能比较必须使用相同口径。

## 2. 实测基线

来源：`data/pipeline-1000/timing-analysis.json`。这是运行中的阶段性快照，最终应在本批结束后补齐，不作为长期稳定吞吐保证。

| 环节 | 已测耗时或当前设置 | 说明 |
|---|---|---|
| 采集 5 条笔记 | 连续 8 批约 87.7–88.2 秒 | 包含 5 × 15 秒主动等待、页面固定等待 5 秒，其余约 8 秒包含启动、请求和关闭 |
| 每批采集结束 | 额外等待 15 秒 | 父进程 `time.sleep(args.delay)`，与每条笔记等待使用同一参数 |
| 图片下载与初筛 | 部分无 VLM 插入区间约 1.1 秒/张 | 由报告间隔扣除批后等待估算；不是纯网络耗时，也未独立分离全部 Live 开销 |
| 图片下载 | 并发 2，每次请求前等 1.5 秒 | 每组使用 gather，整组结束并处理完才发下一组 |
| Live MP4 下载 | 串行，每次请求前等 1.5 秒 | 尚无独立端到端计时 |
| VLM 分类 100 张 | 两轮约 21.5 / 20.2 秒 | 每调用 20 张，共 5 次，2 路并发 |
| VLM 定位 | 39 张约 41.3 秒；16 张约 12.4 秒 | 每调用最多 5 张，2 路并发 |
| 本地结果处理 | 两轮约 23.0 / 13.9 秒 | 包括裁剪、编码、质量检查、去重和入库，未逐项拆分 |
| 完整审核 100 张 | 两轮约 85.8 / 46.4 秒 | 因需要定位的比例不同而变化，不是每轮都超过一分钟 |
| 本地读图、解码、哈希、近似查询 | 离线重放 100 张约 2.9 秒 | 数据库仅数百张，不能直接外推到 100k |
| 审核后等待 | 已设为 0 | 原来的额外 60 秒已取消，不重复计入未来收益 |

较早快照：21.2 分钟净新增 214 张候选，约 605 张/小时；新增 200 张已审核样本中自动保留 125 张。该速度包含早期中断、重启及已经取消的等待，后续以稳定区间重测。

## 3. 优先级与实施顺序

### P0：先补计时，保持基线可比较

涉及：`pipeline.py`、`mediacrawler_worker.py`、`download.py`、`live_download.py`、`vlm_batch.py`、`crop_review.py`。

增加单调时钟计时和 JSONL 事件记录，包含任务 ID、批次 ID、阶段、开始结束时间、耗时、数量及成功/失败类别。不要记录 Cookie、签名 URL 或原始认证信息。

分别记录：

- 浏览器启动、页面就绪、搜索、笔记详情请求，以及每一处主动等待。
- 下载排队、图片网络传输、MP4 网络传输、解码、哈希、近似查询、写盘。
- VLM 排队、图片编码准备、分类调用、定位调用、解析及校验。
- 边界检测、比例修正、PNG 编码、最终去重、数据库提交和预览导出。

并行后分别报告阶段工作时间之和与实际墙钟时间，不能把重叠耗时直接相加。统计中位数、P95、队列积压和当前并发占用。

### P1：消除重复请求与重复初始化

1. 将每个关键词、页码对应的一次搜索结果保存为本地页快照，页内游标引用该快照；不再每取 5 条笔记就重新搜索同一页。
2. 请求详情前查询笔记 ID，已完成笔记直接跳过；新增来源关键词可补记，不重新下载。失败笔记按既有尝试次数和失败类型处理。
3. 缓存中有时效性的请求信息不无限复用；确有失效证据时刷新页面并重新按 ID 去重，而不是在未知异常下反复刷新。
4. 后续将“每 5 条笔记重启进程和浏览器”改为一个任务内复用受管理的 worker 与浏览器。保留明确的总数量上限、会话关闭和崩溃恢复。

收益：减少重复搜索、结果排序变化导致的重复笔记、无效等待及浏览器启动成本。先做页面缓存和 ID 去重，再做长生命周期 worker，便于定位问题。

验收：同一有效页快照只搜索一次；同一已完成笔记不重复请求详情；重启后页快照和游标一致，不丢未处理条目。

### P2：主动延时可配置，删除重复等待

以下均为拟新增配置，不是当前已经生效的参数。CLI 可提供 `--no-fixed-delays` 总开关，覆盖配置中的主动 sleep；仍保留逐项配置，方便对照实验。

| 拟配置 | 当前行为 | 优化方案 |
|---|---|---|
| `fixed_delays_enabled` | 没有总开关 | false 时主动 sleep 为 0；true 时按独立参数执行 |
| `note_interval_seconds` | 15 秒，且命令行限制最少 10 秒 | 允许 0，保留详情请求单路；非零时按请求开始时间约束节奏，避免每次响应后重复累加 |
| `collection_batch_delay_seconds` | 共用 `--delay`，15 秒 | 独立出来，设为 0 |
| `media_delay_seconds` | 图片和 MP4 各等待 1.5 秒 | 设为 0，用并发上限控制在途下载 |
| `vlm_cooldown_seconds` | 当前已为 0 | 保持 0 |
| `page_ready_timeout_seconds` | 固定等 5 秒 | 改为必要状态就绪即继续，设置最大等待时限，而非 sleep 5 秒 |

页面就绪条件应覆盖签名/请求所需页面环境和登录或验证状态，不能仅删除 sleep 后立即请求，也不宜依赖可能一直不结束的全页 network-idle。

关闭主动延时不关闭网络 I/O 等待、超时、并发上限或平台访问异常处理。验证、401/403/429、平台限制仍停止对应采集/下载链路；不自动提高并发或反复重试这些响应。仅瞬时连接故障等另行采用有上限的重试退避，它属于异常恢复，不是每条任务固定休息。

验收：日志能证明主动等待为 0；仍有有限在途请求；限制响应触发停止；0 延时参数能通过主程序与 worker 的一致校验。

### P3：阶段重叠，先不提高平台详情并发

当前流程：

```text
取得 5 条笔记 → 等待 → 图片下载 → Live 下载 → 满 100 张分类
→ 全部分类结束 → 全部定位结束 → 逐张本地处理 → 下一轮采集
```

建议流程：

```text
搜索快照 → 单路笔记详情 → 有界媒体队列 → 图片下载 / Live 下载
                                      ↓
                              解码、哈希、去重
                                      ↓
                              每 100 张形成审核批次
                                      ↓
                         分类 → 所需图片定位 → 本地处理
                                      ↓
                              单写入端提交与导出
```

分两个可独立启停的等级：

**A. 保留 VLM 期间暂停采集的节奏。** 每取得一条笔记就把媒体任务交给下载队列；下载和后续笔记采集重叠。进入 100 张审核时不再启动新详情请求，允许已开始的任务完成。分类结果陆续返回后可提交定位；定位结果一批返回就开始本地裁剪，不等全部定位返回。

**B. 全流水线并行。** 采集、下载和 VLM 持续同时运行，用有界队列形成反压。这个等级取消了原先“VLM 期间暂停采集”的节奏，应在本批结束后的方案讨论中单独确认，再实施。

拟配置 `overlap_mode = off | media | full`，对应串行对照、等级 A、等级 B。默认先测试 media。

初始并发建议：详情 1；图片 2，稳定后对照 4；Live 2；VLM 全局总并发 2，稳定后对照 4；本地 CPU 图像处理先 2 个 worker。分类和定位共用 VLM 全局信号量，不能各设 2 后意外变成总并发 4。

实现要点：

- 以常驻下载 worker 补充空闲槽位，替代一整组 gather 完成后才发下一组的屏障。
- 使用有界队列。初始可设媒体队列 200 个引用、审核待处理队列 200 张；限制在内存中解码的图片数，不能把 200 张原图同时常驻 RAM。
- Live 封面和 MP4 可独立下载，但审核入队前确认配对完成；失败的配对不能冒充完整 Live 进入最终数据集。
- 下载线程/进程返回结果，由单写入端提交 SQLite。不得跨线程共享现有 SQLite connection；数据库事务内不进行网络请求或长时间图像编码。
- 原图与裁剪图写入继续采用临时文件加原子替换。任务状态、阶段版本与唯一键防止重复消费；重启时回收未完成的在途任务。
- 达到 1,000 候选时停止继续提交采集任务，对在途任务做明确的额度预留与结算；重复或不合格项释放预留。队列并行不能让数量上限失控。
- 剩余不足 100 张时显式 flush；最后等待全部下载、Live 配对和审核任务结束，再输出最终报告。

### P4：针对本地处理和 VLM 做增量优化

本地处理优先重用同一张图的解码结果，减少“裁剪 → PNG 编码 → 再次解码检查”的重复工作；图像处理可并行，但最终去重与接受状态需有一致的提交顺序。

保持 VLM 批大小和原尺寸定位要求不变，先测 2→4 并发的实际墙钟收益、失败率、P95 和 token 使用。原尺寸编码、上传与服务端处理成本应分别观察；不通过缩小定位图来换取速度。

近似查询当前不是优先瓶颈。到 10k/100k 索引规模时再测候选桶大小与 P95，不能用当前数百张的 2.9 秒结果断言大规模性能。

## 4. 分阶段实验与验收

等本次 1,000 张任务结束，保存最终数据库统计、清单、配置、计时和预览作为基线。不要覆盖该基线目录。

| 实验 | 变化 | 建议样本 | 目的 |
|---|---|---|---|
| A | 仅增加计时，保持串行及原请求间隔 | 100 张 | 建立稳定、完整的阶段基线 |
| B | 页缓存、笔记去重；取消批后和媒体等待；页面条件等待 | 100 张 | 测重复劳动和重复等待收益 |
| C | 主动延时总开关关闭，详情并发仍为 1，其他同 B | 100 张 | 单独测取消笔记固定间隔的收益与错误情况 |
| D | 使用 B/C 中稳定配置，启用 media 重叠 | 200 张 | 测阶段重叠收益，不混入更多并发变化 |
| E | 单独讨论后启用 full 重叠，再逐项试媒体或 VLM 并发 4 | 200 张 | 测吞吐上限与反压是否有效 |

线上搜索结果会变化，新增图片比例也不同。各实验记录请求笔记数、实际新增笔记数、图数分布、Live 占比和需定位占比。不能只拿两个不同关键词的总耗时直接比较。

下载、哈希、裁剪和队列调度尽量用同一固定清单重放，使用本地 HTTP fixture 测可控的网络延迟；真实线上样本验证端到端收益。VLM 输出有随机性，保留报告并对同一组重点图复核，不将通过率上升直接当作准确率上升。

核心指标：

1. 净新增初筛候选/分钟，以及自动保留模板/小时。
2. 端到端耗时和每阶段 P50/P95、主动 sleep 占比、排队占比。
3. 搜索/详情请求数、重复详情请求数、网络失败与平台验证/限流事件。
4. VLM 完成率、格式异常、总 token 与每张候选 token。
5. 峰值内存、队列长度、写入冲突、Live 未配对数、重启后的重复消费和遗漏。
6. 数据质量：尺寸规则、哈希与近似重复规则、裁剪结果和重点样例不退化。

阶段验收以数据完整、可恢复、无新增平台限制为前提。建议只有在可比较样本上吞吐提升至少 15%，且无明确质量退化时，才把该项作为默认；样本不足则继续验证，不宣称长期稳定。

## 5. 回退与异常处理

- 延时总开关、各项间隔、overlap_mode 和各并发数独立配置，配置及版本写入运行报告。
- 可回到 overlap_mode=off、详情单路、原笔记间隔，保留当前已取消的 VLM 后额外休息。
- 正常切换在批次边界执行：停止提交新任务，排空或持久化队列，再重启。无需删库或重新下载已完成文件。
- 平台访问限制发生时立即停止新增平台请求；保存已取得的成果和游标。仍可完成已落盘图片的本地处理，不为赶目标反复重试受限请求。
- VLM 暂时不可用时由队列上限暂停继续积累，保留可恢复状态；失败调用不让已完成的整批结果丢失，按阶段保存检查点。

## 6. 预期收益与下一步决策

每 5 条笔记的约 88 秒采集加 15 秒批后等待，约 95 秒来自固定等待；这表明主动延时是主要优化空间之一，但不能据此保证去掉后长期快十倍。

保持详情请求间隔不变，仅做下载/处理重叠，先前估计整体可能提升 20%–40%，这是待验证的假设。取消间隔与全流水线并行的收益不能简单相乘：最终速度由最慢阶段、重复率、Live 占比和平台响应共同决定。

本批结束后的讨论顺序：先看 1,000 张的最终新增速度与质量，再选择 B/C 的主动延时配置，然后确定是否保留 VLM 期间暂停采集，最后才提高媒体和 VLM 并发。
