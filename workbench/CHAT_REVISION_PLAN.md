# 交付后的对话修改方案

状态：2026-10-09 第一版已实现本机对话入口、SDK执行队列、工作副本复核发布及换图/改文案。本文保留原方案；历史分支、撤销和远程客户登录仍为后续范围。

## 产品行为

交付完成表示某个版本制作结束，任务仍可继续修改。客户在现有工作台中查看成图，通过右侧对话框提出修改；每轮修改形成新版本，与原参考图和修改前版本对照。沿用同一仓库的 skill / workbench，不另建项目。

建议以“对话＋选中对象”为主。客户可以直接说“右上角的照片换成另一张”，也可以先点击照片、贴纸或文字，选中对象自动附在消息中。系统根据当前版本、选中对象、客户素材和修改历史理解需求；指代不明确时只问必要的一个问题。

需求明确且属于支持的修改时直接执行，在消息中展示简短改动摘要。不是每句话都弹确认。涉及整体重排、具体文案不明或新增生成范围不明时，先澄清范围；不默默扩大修改。

示例：客户选中右下照片，输入“放大人物，别切到头，白便签放到照片前面”。页面显示“调整照片裁切；将白便签移到照片上方”，随后展示制作进度。完成后回复“已生成v3，人物裁切和白便签层级已调整”，附v2/v3对照、改动对象和复核结论。

## 修改流程与版本

首次制作继续使用现有六步。交付后的修改采用较短的四个状态：理解修改 → 执行修改 → 对照复核 → 新版本可用，避免看起来每次都从头提取。

每条修改请求绑定 task_id、request_id、base_version_id 和所选 object_ids。执行前再次核对基础版本。客户正在查看历史版本时，应明确显示“基于v2修改”；不能把消息悄悄应用到最新v5。

一轮请求对应一个修改记录，可以包含执行前后摘要、耗时、复核问题及多个中间产物。对客户发布经复核的新版本，保留旧版本。失败时保留上一张可用成图，并提供该请求的重试入口；重试使用相同请求身份与已完成素材，避免重复提交远端提取。

“撤销上一轮”创建新的恢复版本，不能删除版本历史。要支持从历史版本继续修改，需要增加可写的工作副本与父版本关系；当前图片快照展示不等于已经实现了可恢复编辑状态。

## 分阶段范围

| 阶段 | 客户能力 | 现有基础与所需补充 |
|---|---|---|
| 第一版 | 移动、裁切、大小、遮挡层级、支持的字体样式；查看改动和前后对照 | 复用 apply 与 review，受现有对象和几何保护规则约束 |
| 第一版 | 从已有客户素材换照片；修改独立文字内容 | 需要在 skill 增加受校验的替换/文案操作；现有 apply 不能直接承担所有换图和改文案需求 |
| 第一版 | 当前任务对话、排队、刷新恢复、每轮耗时、失败重试 | workbench 增加持久化请求记录、执行器和进度推送 |
| 后续 | 从历史版本另起修改分支、撤销恢复 | 先补齐可恢复工作状态、资源哈希和父版本关系，不能只复制成图 |
| 后续 | 局部素材精修、重提取、新生成、整体重排 | 单独定义操作范围与复核标准；保留已成功素材并展示额外处理动作 |

客户提出超过当前能力的修改时，应明确解释限制和可执行的替代操作。例如固定提取相框不能任意变形；含有嵌入文字的贴纸不能当作普通文本直接替换。

## 工程边界

workbench 负责客户对话、任务权限、请求队列、版本展示、事件推送。skill 负责受校验的图像操作、素材来源、成图、复核和版本证据。二者通过任务目录、结构化请求和事件协议衔接，不把图像处理逻辑写进前端。

服务默认只读，加 `--enable-chat` 后启用独立执行器。浏览器提交请求后即使关闭页面，任务也继续运行。消息与任务状态持久化，刷新后恢复对话和进度。

建议链路：

```text
客户消息＋当前版本＋选中对象
    → workbench 保存修改请求
    → 串行执行器读取当前工作状态与对话
    → Agent 生成受限的结构化修改操作
    → skill 校验并执行
    → 查看前后对照并登记复核
    → 发布新版本和改动摘要
```

执行器沿用已验证的 Codex SDK 调用方式，模型初始延续 gpt-5.6-sol / medium。上下文以真实任务文件与版本为准，不能仅依赖聊天记忆。客户文本不直接拼接成命令执行。

按照现有测试偏好，初始执行器设为全局单并发；同任务也串行。排队时间、实际执行时间、远端等待和本地处理分别记录。重复点击发送使用同一幂等键；新消息到达正在执行的任务时先排队，到执行时核对基础版本，必要时说明冲突。

正式提供远程客户访问时增加登录与任务访问权限，图片和消息限制在各自任务内。服务端管理凭据；页面只显示客户需要理解的过程与失败原因。

## 第一版验收

- 完成一次“移动贴纸＋照片裁切＋前后层级”修改，原版本保持可用。
- 从客户素材列表换图，来源校验通过；不存在生成替代客户人物。
- 修改独立文字，不重复叠加已有文本，也不修改提取贴纸中的嵌入文字。
- 刷新、关闭并重开页面后，消息、队列和执行阶段一致。
- 连续发送两条消息按顺序执行；每条显示所基于版本与独立耗时。
- 下载失败时保留成功资源，重试不重复提交已经完成的提取任务。
- 视觉仍存在问题时显示“有待改问题”，不能用脚本成功自动代替视觉通过。

建议先实现已有成图的受限修改闭环，再扩展到任意自然语言重做整张。第一版最重要的是客户可以看懂系统改了什么，结果可核对，旧版本可找回。

## 后续：SVG编辑画布（尚未实现）

当前已支持点选成图对象并通过对话修改；尚未支持画布直接拖动、旋转、缩放或双击编辑文字。

客户提出SVG展示需求后，建议下一阶段将画布做成混合SVG：照片和提取透明贴纸使用image节点，独立文字和规则几何使用对应SVG元素。每个节点关联scene对象ID，选择、拖动等交互转换成同一套结构化修改操作，保存仍经过skill校验与版本发布。不能只把整张PNG放进一个SVG就宣称元素可编辑。

编辑预览可用SVG，正式成片继续提供现有PNG渲染；另提供自包含SVG导出时，应嵌入图片资源并处理字体可移植性。提取贴纸中的嵌入文字、复杂像素纹理仍不可直接当作独立矢量对象编辑。SVG预览与正式渲染要验证裁切、遮罩、字体、阴影和旋转的一致性；在此之前不能承诺SVG和PNG像素完全一致。
